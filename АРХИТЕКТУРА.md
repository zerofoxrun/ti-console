# TI Console — инструкция разработчика

**Для кого:** тот, кто будет менять этот код. Документ отвечает на три вопроса:
из чего состоит расширение, что за что отвечает и чего здесь нельзя делать.

**Главное, что надо понять до первой правки:** этот проект защищается не от
падений, а от **молчаливых отказов**. Кнопка, которая «сработала» и не сделала
ничего; парсер, который придумал индикатор; предупреждение, которое нельзя
проверить; барьер, вокруг которого можно пройти. Всё остальное в архитектуре
следует из этого.

---

## 1. Что это такое

Firefox-расширение в формате **Manifest V3**, работающее **полностью локально**.
Сервера нет: нет бэкенда в рабочем контуре, нет синхронизации, нет общего
хранилища. Данные расследования лежат в `browser.storage.local` профиля.

В репозитории есть каталог `backend/` — это **необязательный** серверный
компонент (обогащение по API, метапоиск, анализ моделью). Он не нужен для
работы браузера и в текущей поставке не разворачивается. Его код важен по
другой причине — см. раздел 7 про паритет.

### Состав

```
extension/
  manifest.json          MV3, event page (НЕ service worker)
  background.js          фоновый скрипт: меню, значок, маршрутизация
  content/scan.js        разбор открытой страницы; внедряется по требованию
  newtab/                консоль: главный экран (три вкладки)
  panel/                 боковая панель
  popup/                 окно по значку: разбор одного значения
  lib/                   чистая логика, покрытая тестами
  data/tools.json        реестр сервисов и плейбуков
  vendor/pdfjs/          pdf.js, лежит внутри расширения
policies/                корпоративная политика Firefox и её генератор
backend/                 необязательный сервер (не в поставке)
tools/                   сборка демо, аудит интерфейса, съёмка документации
docs/                    документация и картинки к ней
```

## 2. Слои и их границы

![Слои расширения](img/d4-arch.png)

**Правило слоёв:** `lib/` не знает про DOM и про `browser.*`. Всё, что там
лежит, — чистые функции над данными. Именно поэтому оно покрывается тестами,
запускаемыми обычным `node file.test.js`, без браузера и без харнесса.

Интерфейсные файлы (`newtab.js`, `panel.js`, `popup.js`) знают про DOM
и про `browser.*`, но **не содержат логики принятия решений**. Если в обработчике
клика появляется ветка «а тут решаем, можно ли» — она должна переехать в `lib/`
и получить тест.

## 3. Что за что отвечает

### 3.1 `lib/` — ядро

| Файл | Отвечает за | Ключевое |
|---|---|---|
| `ioc.js` | Извлечение индикаторов из текста, снятие дефанга, типы, флаги, выгрузка STIX | Самый важный файл проекта. Зеркало — `backend/app/detect.py` |
| `noise.js` | Отсев шума: имена файлов, версии ПО, обвязка страницы | Отсеянное не удаляется, а помечается |
| `cases.js` | Кейсы: создание, активный, добавление, импорт, миграция старого формата | Единственная точка входа «положить в кейс» |
| `timeline.js` | Хронология кейса и сводка для передачи смены | Текст заметок в хронологию не пишется |
| `playbook.js` | Планирование плейбука: какие шаги выполнятся и почему отброшены остальные | Здесь же применяется TLP-гейт |
| `query.js` | Сборка поискового запроса: профили площадок, шаблоны, ограничения | Возвращает, какие площадки применены и какие отброшены |
| `textools.js` | base64, URL, hex, хеши, дедупликация, сравнение списков | Чистые вычисления, ни одного сетевого вызова |
| `fetchpage.js` | Забор страницы по ссылке: нормализация, отсев схем и внутренних зон, риски конкретной ссылки | `credentials: 'omit'`, `referrerPolicy: 'no-referrer'`, разбор через `DOMParser` |
| `pdftext.js` | Извлечение текста из PDF через pdf.js | `isEvalSupported: false` — иначе CSP расширения не даст работать |
| `casegraph.js` | Схема кейса: узлы и рёбра двух типов | Никогда не выдумывает узел |
| `triage.js` | Очередь «входящие на триаж» | Отбой помнится, обрезка называется вслух |
| `analyze.js` | Клиент языковой модели | Работа приостановлена; кнопки скрыты, пока модель не задана политикой |

### 3.2 `background.js` — фоновый скрипт

Отвечает за:

- контекстное меню (создаётся **на верхнем уровне**, а не в `onInstalled`);
- значок на панели и счётчик на нём;
- маршрутизацию сообщений между content-скриптом, панелью и консолью;
- внедрение `content/scan.js` по кнопке;
- системные уведомления об отказах.

**Две ловушки MV3, на которых этот файл уже спотыкался:**

1. **Это event page, а не service worker.** Firefox MV3 service worker
   не поддерживает: скопированный из документации Chrome пример не загрузится.
2. **Страница выгружается при простое.** `runtime.onInstalled` при пробуждении
   не срабатывает. Поэтому контекстное меню создаётся на верхнем уровне модуля,
   с `contextMenus.removeAll()` перед созданием — иначе после пробуждения меню
   исчезало, а при повторном создании падало с «duplicate id».

### 3.3 `content/scan.js` — разбор открытой страницы

Внедряется **по требованию** через `scripting.executeScript` вместе с `lib/ioc.js`.
Постоянного content-скрипта на всех страницах нет — это принципиально,
см. раздел 5.

Собирает видимый текст плюс значения `href`/`src`/`data-*` (индикаторы часто
лежат в ссылках, а не в тексте), прогоняет через тот же `IOC.extractIocs`,
подсвечивает найденное и отдаёт в background.

**Известное ограничение, которое нельзя обойти:** содержимое внутри closed
shadow DOM недоступно.

### 3.4 Интерфейс

| Экран | Файл | Чем задан |
|---|---|---|
| Консоль (новая вкладка) | `newtab/newtab.js` | `chrome_url_overrides.newtab` |
| Консоль (домашняя страница) | тот же | `chrome_settings_overrides.homepage` |
| Боковая панель | `panel/panel.js` | `sidebar_action` |
| Окно по значку | `popup/popup.js` | `action.default_popup` |

Два экрана консоли подменяются **разными механизмами**, и это не дублирование:
в адресе `moz-extension://` UUID случайный для каждого профиля, поэтому политика
`Homepage` его написать не может. Политики `Homepage` в сборке нет намеренно —
она имеет приоритет над настройкой расширения и вернёт страницу Firefox.

## 4. Как файлы `lib/` загружаются — и почему это важно

В HTML они подключаются обычными `<script>` и делят **одну глобальную область**:

```html
<script src="../lib/ioc.js"></script>
<script src="../lib/cases.js"></script>
...
<script src="newtab.js"></script>
```

Из этого следуют два правила:

**1. Два `const API` в разных файлах дают `SyntaxError`, который валит страницу
целиком, ещё до отрисовки.** Поймано ровно так: `fetchpage.js` и `analyze.js`
оба объявляли `API`. В `test:config` стоит проверка пересечения глобальных имён;
она понимает разницу между файлом, завёрнутым в IIFE, и незавёрнутым.

**2. Файлы, внедряемые в страницу, обязаны быть идемпотентны.** Все инъекции
в один документ делят один sandbox: второе внедрение `ioc.js` в ту же вкладку
падало бы на повторном `const`. Поэтому такие файлы обёрнуты в guarded IIFE:

```js
(function initTriage() {
  if (globalThis.TITriage && typeof globalThis.TITriage.addMany === 'function') return;
  ...
  globalThis.TITriage = API;
})();
```

Экспорт двойной — `module.exports` для тестов в node и `globalThis` для браузера.

## 5. Разрешения: что запрошено и чего нет

```json
"permissions": ["storage", "contextMenus", "activeTab", "scripting",
                "tabs", "browserSettings", "dns", "notifications"],
"optional_host_permissions": ["<all_urls>"]
```

| Решение | Причина |
|---|---|
| `activeTab` + `scripting` вместо `<all_urls>` | Расширение с доступом ко всем страницам читает почту и админки аналитика. Доступ выдаётся к той вкладке, где нажата кнопка, и на время действия |
| `<all_urls>` только в `optional_host_permissions` | Запрашивается у аналитика при первом заборе страницы по ссылке, видно в `about:addons` |
| `dns` вместо запроса к ipinfo | Запрос к внешнему сервису отправил бы туда историю посещений аналитика |
| `notifications` | Отказ разобрать страницу виден там, куда смотрит человек. Тост в консоли виден тому, кто смотрит на консоль, — а он смотрит на страницу |
| `webRequest`, `cookies`, `history` **не запрошены** | В CI стоит проверка, что они не появятся |

### CSP расширения

```
script-src 'self'; object-src 'none'; connect-src 'self' https:
```

`https:` — это scheme-source: разрешён **любой** https-адрес. Ослабление
сделано осознанно, ради разбора отчётов по ссылке, где адрес произволен
по условию задачи. Разбор размена лежит в `_comment_csp` манифеста, и
`test:config` требует, чтобы этот блок существовал.

**Сужать `connect-src` на этапе сборки нельзя.** Так уже было: в репозитории
стояло `https:`, а задача сборки подменяла директиву закрытым списком — и
в собранном XPI забор по ссылке молча не работал. Проверка в `test:config`
падает, если присваивание вернётся.

## 6. Реестр `data/tools.json`

Запись сервиса:

```json
{
  "id": "vt-ip",
  "name": "VirusTotal",
  "category": "network",
  "types": ["ipv4", "ipv6"],
  "url": "https://www.virustotal.com/gui/ip-address/{{ioc}}",
  "exposure": "public",
  "activity": "passive",
  "auth": false,
  "note": "Вердикты вендоров, связанные семплы, пассивный DNS",
  "pricing": "free-account",
  "api": "free-personal"
}
```

Подстановка значения — `{{ioc}}` (кодированное) или `{{ioc_raw}}` (как есть).
Категорий девять: `network`, `domain`, `file`, `email`, `vuln`, `actor`,
`crypto`, `code`, `reference`.

Два поля несут ответственность, остальные — удобство:

- **`exposure`** (`public` / `limited`) — станет ли индикатор известен третьей
  стороне. На нём держится TLP-гейт;
- **`api`** (`none` / `free-personal` / `free-commercial` / `paid` /
  `unverified`) — можно ли опрашивать автоматически, не нарушая ToS. Бесплатные
  тарифы VirusTotal, AbuseIPDB и OTX запрещают коммерческое использование,
  и санкция VT — бан организации.

**Реестр закрыт.** Кнопки «предложить инструмент» в интерфейсе нет намеренно:
запись, появившаяся мимо ревью, этих полей не имеет — значит, в клиентском
режиме она не скроется, потому что система не знает, что сервис публичный.
Один такой сервис обесценивает весь гейт. В CI стоит проверка, что путь
добавления не появился.

Плейбук — это список `id` инструментов в осмысленном порядке. Порядок
и есть содержание: бесплатное раньше, расходующее квоту позже.

## 7. Паритет клиента и сервера

`extension/lib/ioc.js` и `backend/app/detect.py` — **зеркала**. Один и тот же
текст обязан давать один и тот же результат независимо от того, есть сервер
или нет. Иначе один и тот же отчёт разбирался бы по-разному в зависимости
от конфигурации, и объяснить аналитику расхождение было бы нечем.

Паритет проверяется `backend/tests/test_parity.py`: общий корпус прогоняется
через обе реализации, результаты сравниваются.

**Правило при правке парсера:** меняете `ioc.js` — меняете `detect.py` в том же
коммите, добавляете случай в корпус паритетного теста. Иначе тест упадёт, и это
правильное поведение.

То же относится к `lib/analyze.js` ↔ `backend/app/analyze.py`.

## 8. Хранилище

Всё в `browser.storage.local` профиля:

| Ключ | Что лежит |
|---|---|
| `ti_cases` | Кейсы целиком |
| `ti_active_case` | Идентификатор активного |
| `ti_triage` | Очередь входящих и список отбоя |
| `ti_last_scan` | Результат последнего разбора страницы (для панели) |
| `ti_tlp_mode` | Режим данных |
| `ti_theme`, `ti_hide_paid`, `ti_searx_url` | Настройки интерфейса |
| `ti_scan_deny_local` | Локальные дополнения к списку запрета разбора |
| `ti_case_items`, `ti_case_timeline` | Старый формат одиночного кейса; читаются только при миграции |

Настройки из политики приезжают в `browser.storage.managed` ключом
`3rdparty.Extensions."ti-console@soc.internal"` и доступны **только на чтение**.

⚠️ **Ловушка, которая уже стоила потерянной работы аналитика.** Панель писала
в `ti_case_items`, вкладка читала `ti_cases`, комментарий утверждал, что ключи
совпадают. Панель отвечала «+7», в кейсе не появлялось ничего. Отсюда правило:
**одна точка входа на операцию.** «Положить в кейс» живёт в `cases.js` и
вызывается отовсюду; после записи рассылается сообщение `cases-changed`.

## 10. Чего здесь нельзя делать

Это не пожелания, а границы, за которыми продукт перестаёт быть тем, чем он
задуман.

| Нельзя | Почему |
|---|---|
| Отправлять индикатор, содержимое страницы или контекст инцидента куда-либо автоматически | Единственный исходящий запрос — забор страницы по явно введённой ссылке, и он выключается политикой |
| Подключать MISP, OpenCTI, TheHive, Elastic, облачные сервисы | Клиентские данные не должны попадать в системы, которые их хранят |
| Добавлять интеграцию с языковой моделью в обход текущего решения | Работа приостановлена решением SOC |
| Делать синхронизацию между аналитиками | Общей памяти команды нет |
| Требовать сервер для чего-то нового | Всё предлагаемое должно работать без него |
| Смешивать клиентов в одном кейсе | Функция, способная смешать данные разных заказчиков, отклоняется |
| Запрашивать `<all_urls>` в `permissions` | Только `optional_host_permissions`, только по согласию аналитика |
| Класть ключи API в расширение или в политику | Именно за это отклонён VT4Browsers |
| Сужать `connect-src` на этапе сборки | См. раздел 5 |
| Прятать закрытое режимом данных | Закрытое зачёркивается: аналитик должен видеть, чего лишился |

## 11. Тесты

```bash
# ядро и интерфейсные проверки — обычный node, без браузера
for f in extension/lib/*.test.js extension/*.test.js extension/newtab/*.test.js; do
  node "$f" || break
done

# сервер
cd backend && python3 -m pytest -q && cd ..

# согласованность политики, манифеста и реестра
python3 tools_run_ci_check.py
```

Сейчас: **848 проверок в браузерной части, 48 в серверной**, `addons-linter`
без ошибок.

### Как здесь принято писать тест

Три правила, каждое появилось из настоящего дефекта:

1. **Название теста — это утверждение о продукте, а не о функции.**
   `ПЕРВЫЙ РАЗБОР ПЕРЕЖИЛ ВТОРОЙ` полезнее, чем `addMany works`.
2. **У проверки есть объяснение, зачем она.** Второе поле `check(...)`
   печатается при провале и отвечает на вопрос «а что сломается, если так
   сделать».
3. **Новая проверка обязана быть протестирована негативно.** Сломайте то, что
   она должна ловить, убедитесь, что она падает, верните. Проверка, которая
   никогда не падала, не защищает ни от чего.

Третье правило — не абстракция. В этом проекте уже были: проверка разметки,
находившая искомую строку в комментарии и потому всегда зелёная; проверка
глобальных имён, дававшая пять ложных срабатываний на исправном коде; проверка,
требовавшая файл, которого нет в репозитории.

### Аудит интерфейса

```bash
python3 tools_build_demo.py
PLAYWRIGHT_MODULE=$(node -e "console.log(require.resolve('playwright'))") \
CHROMIUM_PATH=/opt/pw-browsers/chromium \
node tools/ui-audit/clicks.mjs
```

Нажимает каждую кнопку и смотрит, произошло ли хоть что-нибудь. Ловит три вида
молчаливых дефектов: исключение в обработчике; кнопка без реакции; реакция
не туда (открылось окно или скачался файл там, где не должно).

Отдельно `tools/ui-audit/panel.mjs` — боковая панель с подставным `browser.*`,
и `tools/ui-audit/csp-connect.mjs` — опыт, показывающий, что делает `connect-src`
с запросом на чужой источник.

### Картинки документации

```bash
PLAYWRIGHT_MODULE=... node tools/docs-shots/shots.mjs
```

Снимает все скриншоты с демо-сборки и рисует схемы из исходников рядом. Цифры
на схеме режима данных подставляются из реестра: схема с числом, разъехавшимся
с реестром, врёт читателю о размере доступного, и глазами это не заметить.

## 12. Сборка и выпуск

```bash
python3 tools_build_ext.py     # ti-console.xpi и ti-console-theme.xpi
python3 policies/make-local.py # политика без ссылок на сервер
python3 tools_build_demo.py    # демо-страница для аудита и снимков
```

Конвейер (`.gitlab-ci.yml`) состоит из четырёх стадий: `test`, `build`,
`package`, `deploy`. Проверки конфигурации живут в задаче `test:config`
и покрывают то, что не поймает ни один юнит-тест: согласованность адресов
в политике и CSP, отсутствие политики `Homepage`, отсутствие запрещённых
разрешений, целостность плейбуков, закрытость реестра.

Версия расширения в `manifest.json` — источник правды; `CHANGELOG.md`
и `СОСТОЯНИЕ.md` обязаны с ней совпадать. Реестр инструментов версионируется
отдельно: его можно обновить, пересобрав только расширение.

## 13. Если правите парсер

Самый опасный файл в проекте. Один случай из практики, чтобы было понятно,
какого рода ошибки здесь возможны.

Парсер **придумал индикатор**, которого в отчёте не было. В тексте шёл обычный
список:

```
https://evil.example/gate.php
d41d8cd98f00b204e9800998ecf8427e
CVE-2025-31324
```

Логика «значение перенесено на следующую строку» склеила первую строку
со второй и выдала `https://evil.example/gate.phpd41d8...`. Шесть MD5,
записанных столбиком, превратились в три несуществующих SHA-256.

Лечится правилом «список — не перенос»: склейка отвергается, если правая
строка сама по себе является законченным значением, начинается со схемы или
содержит пробел; для hex — если строк одинаковой длины три и больше.

Отсюда общее правило для этого файла: **сомнение трактуется в сторону
«не склеивать»**, а всё, что всё-таки склеено по догадке, помечается
`ambiguous:wrap` и показывается в двух формах — как в исходнике и как склеено.

Любая правка парсера идёт вместе с правкой `backend/app/detect.py` и новым
случаем в корпусе паритетного теста.
