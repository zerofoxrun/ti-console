# Локальная версия: развёртывание без сервера

Короткая инструкция на тот случай, когда сервера нет и пока не будет.
Полный RUNBOOK описывает 16 этапов и предполагает арендованную или
внутреннюю ВМ; здесь — два часа работы и ни одного серверного компонента.

**Это не демо-режим и не урезанная сборка.** Расширение то же самое,
код тот же. Отсутствует ровно то, что физически требует сервера.

---

## Что работает и чего не будет

| Работает | Не работает |
|---|---|
| Дерево из 87 инструментов и 6 плейбуков | Автоматическое обогащение по API |
| Умный поиск: 18 типов индикаторов, дефанг, дедупликация | Метапоиск через SearXNG |
| Разбор открытой страницы с подсветкой | Активный парсинг (краулер) |
| Боковая панель | Журнал аудита |
| Кейс, экспорт CSV / JSON / STIX 2.1 | Общий кеш и общая квота |
| **Анализ моделью — через API провайдера** (см. ниже) | |
| Скелет отчёта в Markdown | |
| Тёмное оформление | |
| Блокировка сторонних расширений | |
| Глобальный поиск в резервном режиме (`site:`) | |

Обогащение никуда не девается — оно становится ручным: аналитик
открывает инструмент из дерева одним кликом вместо того, чтобы искать
закладку. Это и есть основной сценарий, ради которого всё затевалось.

**Что вы теряете как MSSP:** журнал того, какой индикатор в какой
внешний сервис ушёл. Пока обогащение ручное, его и нет — фиксировать
нечего, аналитик открывает сайты сам. Но помнить об этом надо: с
появлением автоматики журнал становится обязательным.

## Два решения до начала

### Решение 1. Подпись расширения `[ОБЯЗАТЕЛЬНО]`

Firefox не ставит неподписанные расширения. Варианты:

| Вариант | Как | Плюс | Минус |
|---|---|---|---|
| **A. Отключить проверку подписи** | AutoConfig на ESR (шаг 4) | Ничего никуда не уходит, делается за 10 минут | Снимается платформенная защита на машине |
| **B. Подписать в AMO** | Загрузить XPI на addons.mozilla.org как **unlisted** | Подпись настоящая, защита остаётся | Код расширения уходит в Mozilla |
| **C. Временная загрузка** | `about:debugging` → «Загрузить временное дополнение» | Ноль настроек | **Живёт до перезапуска браузера** |

**Рекомендация: C для показа, A для пилота.** Вариант C годится, чтобы
за минуту показать инструмент на встрече, и не годится для работы.
Вариант A на ESR штатный: `xpinstall.signatures.required` действует
только на ESR, Developer Edition и Nightly, и снятая проверка
компенсируется белым списком `ExtensionSettings`, который блокирует
установку всего, кроме трёх наших дополнений.

Вариант B имеет смысл, когда дойдёте до массовой раскатки и ИБ
скажет, что снимать проверку подписи нельзя. Решение обратимо:
подписанный XPI ставится той же политикой, AutoConfig просто убирается.

### Решение 2. Где лежат XPI на машине

Политика ставит расширения с диска по пути `file:///`. Нужен каталог,
который есть на всех машинах и доступен пользователю на чтение:

```
Windows:  C:\TI-Console\        <- цель по умолчанию
Linux:    /opt/ti-console/
```

⚠️ **Каталог в корне диска, а НЕ в `C:\Program Files\`** — и это
не вкусовщина. Program Files добавляет три независимых способа получить
`ERROR_NETWORK_FAILURE`, причём ни один не виден в Проводнике:

1. **VirtualStore.** Запись в Program Files требует прав администратора.
   Если копирование прошло без повышения прав, Windows перенаправляет
   его в `%LOCALAPPDATA%\VirtualStore\Program Files\…`. Проводник
   показывает файл на месте — он склеивает оба вида, — а по настоящему
   пути файла нет, и Firefox его не находит. Это самая частая причина
   и самая обидная: глазами всё правильно.
2. **Пробел требует кодирования в `%20`.** Ошибка в одном символе даёт
   ту же самую ошибку без уточнений.
3. **ACL на Program Files строже**, и при ручной правке прав легко
   отобрать чтение у пользователя.

Каталог без пробелов в корне диска снимает все три разом.

Сетевая шара тоже работает, но тогда браузер при старте зависит от её
доступности — на ноутбуке вне сети расширение не поставится.
Локальный каталог надёжнее.

⚠️ **Имена файлов на диске и в политике обязаны совпадать в точности.**
Звучит очевидно, спотыкаются ровно на этом: сборка выдаёт
`ti-console-0.12.1.xpi`, политика ждёт `ti-console.xpi`, расширение
не ставится — а `about:policies` при этом показывает всё зелёное.
Увидеть можно только в `about:addons` по отсутствию дополнения.

Поэтому файлы называются **без версии**: версия лежит внутри манифеста
и видна в `about:addons`, а в имени файла она только создаёт рассинхрон
при каждом обновлении.

## Шаг 1. Собрать пакеты `[ЛОКАЛЬНО]`

Если вам прислали готовые `ti-console-*.xpi` — пропускайте шаг.

```bash
# тесты расширения — 924 проверки
node extension/lib/compat.test.js
for f in extension/lib/*.test.js; do node "$f"; done
node extension/markup.test.js
node extension/background.test.js
node extension/newtab/fox.test.js

# Сборка обоих пакетов. Имена БЕЗ версии — ровно такие ждёт политика.
python3 tools_build_ext.py
ls -lh dist/*.xpi
```

Собирать `zip`-ом напрямую **не надо**: сборщик вычищает из манифестов
комментарии (`_comment_*`). В репозитории они полезны, в установленном
расширении дают предупреждения, а внутри объекта `theme` — риск того,
что тема не встанет вовсе: этот объект Firefox валидирует строго.

## Шаг 2. Собрать локальную политику `[ЛОКАЛЬНО]`

```bash
python3 policies/make-local.py            # Windows, по умолчанию
python3 policies/make-local.py --linux    # если нужен вариант под Linux
python3 policies/make-local.py --server   # позже, для серверной версии
```

Генератор вычищает из результата все ключи-комментарии. Это не косметика:
Firefox пишет в `about:policies` → Errors строку «Unknown policy» на
**каждый** такой ключ, и полтора десятка наших же комментариев превращают
вкладку Errors в шум, в котором тонет настоящая ошибка. Правило простое:
`policies/policies.json` документирован, разворачиваемый файл чист.

Файл `policies/policies-local.json` собирается из основного, из него
убрано всё, что ссылается на сервер. Руками его не правят — правки
вносятся в `policies/policies.json` и генератор запускается заново.

Пути к XPI уже проставлены под Windows, менять их не нужно:

```json
"ti-console@soc.internal": {
  "install_url": "file:///C:/TI-Console/ti-console.xpi"
},
"ti-console-theme@soc.internal": {
  "install_url": "file:///C:/TI-Console/ti-console-theme.xpi"
}
```

Прямые слэши — требование формата `file:///`, обратные Firefox не примет.

**Что действительно надо заменить** — список внутренних зон
в `WebsiteFilter`. Там заглушки `*.internal`, `*.corp`, `*.local`;
подставьте свои, иначе барьер к внутренним системам ничего не закрывает.

## Шаг 3. Установить Firefox ESR `[АРМ]`

Именно **ESR**, а не обычный Firefox: на обычном не работает отключение
проверки подписи, и цикл обновлений там другой.

Загрузка — с сайта Mozilla, раздел Enterprise. Windows: MSI, ставится
штатным средством раскатки. Linux: пакет из репозитория дистрибутива
или tarball в `/opt`.

## Шаг 4. Разложить файлы `[АРМ]`

### Windows

```
C:\TI-Console\ti-console.xpi
C:\TI-Console\ti-console-theme.xpi
C:\Program Files\Mozilla Firefox\distribution\policies.json   <- policies-local.json
```

Проверьте, что файлы действительно там, **не глазами в Проводнике**,
а командой — Проводник склеивает настоящий каталог с VirtualStore
и показывает файлы, которых по пути нет:

```cmd
dir /b "C:\TI-Console\"
```

Ожидается ровно две строки: `ti-console.xpi` и `ti-console-theme.xpi`.
Если видите `ti-console.xpi.xpi` — Проводник скрывает расширения,
и файл при сохранении получил второе. Если видите `(1)` — браузер
не перезаписал старый файл, а положил рядом.

Для варианта A (без подписи) ещё два файла:

```
C:\Program Files\Mozilla Firefox\defaults\pref\autoconfig.js
C:\Program Files\Mozilla Firefox\firefox.cfg
```

`autoconfig.js`:

```javascript
// первая строка ОБЯЗАНА быть комментарием — Firefox её игнорирует
pref("general.config.filename", "firefox.cfg");
pref("general.config.obscure_value", 0);
```

`firefox.cfg`:

```javascript
// первая строка ОБЯЗАНА быть комментарием
lockPref("xpinstall.signatures.required", false);
```

⚠️ **Два места, где спотыкаются все.** Первая строка обоих файлов —
комментарий, иначе Firefox молча проигнорирует файл. И переводы строк
должны быть **LF, а не CRLF**: блокнот Windows по умолчанию пишет CRLF,
и AutoConfig не применяется без единого сообщения об ошибке.

### Linux

```
/etc/firefox/policies/policies.json      <- policies-local.json
/opt/ti-console/ti-console.xpi
/opt/ti-console/ti-console-theme.xpi
```

Для варианта A: `/usr/lib/firefox/defaults/pref/autoconfig.js`
и `/usr/lib/firefox/firefox.cfg` (путь зависит от дистрибутива —
проверьте, где лежит исполняемый файл).

## Шаг 5. Первый запуск `[АРМ]`

```
about:policies    -> вкладка Active: политики применились
about:policies    -> вкладка Errors: ДОЛЖНА БЫТЬ ПУСТОЙ
about:addons      -> TI Console, TI Console Dark, uBlock Origin
```

⚠️ Ошибки в `policies.json` Firefox при запуске не показывает — только
на вкладке Errors. Битый файл применяется **частично**, и это выглядит
как «половина настроек не работает».

Вкладка Errors должна быть **пустой**. Если там строки «Unknown policy:
_что-то» — вы развернули `policies/policies.json` (исходник
с комментариями) вместо сгенерированного `policies-local.json`.

## Пилот

Две-три недели, 2–3 аналитика. Что замерить **до** установки:

| Метрика | Как снять |
|---|---|
| Время на проверку одного индикатора | Секундомер, 10 индикаторов, среднее |
| Сколько вкладок открыто в конце дня | Посчитать |
| Сколько времени занимает сборка отчёта | Спросить, записать |

Те же три метрики через две недели. Это единственное основание
для разговора о ресурсах под сервер: цифры «было — стало», а не
обещание пользы.

Отдельно собрать: **какими инструментами из дерева не пользовались
ни разу.** Кандидаты на удаление — реестр должен уменьшаться,
а не расти.

Быстрее, чем установка:


## Нейросеть без сервера

Сервера в этой конфигурации нет, а до сих пор к модели ходил именно он —
держал ключ, считал квоту, вёл журнал. Поэтому расширение обращается
к API провайдера **напрямую**.

### Что при этом теряется — принять до включения, а не после

| | Через сервер | Напрямую из браузера |
|---|---|---|
| Где ключ | на сервере | **в политике на машине аналитика** |
| Общий кеш | есть | нет, одинаковые запросы оплачиваются дважды |
| Журнал аудита | есть | нет |
| Запрет на клиентские данные | проверка на сервере, обойти нельзя | только интерфейс |

**Про ключ прямо.** Он лежит в `policies.json` и попадает в
`browser.storage.managed`. Оттуда его читает и сам аналитик через
`about:debugging`, и любой код, получивший исполнение в контексте
расширения. Считайте ключ известным всем, у кого есть доступ к машине.

**Единственная работающая защита — жёсткий лимит трат у провайдера.**
Не «следить за счётом», а именно ограничение, после которого ключ
перестаёт работать. Поставьте его до того, как раздадите ключ на машины.
При утечке вы теряете сумму лимита, а не сумму со счёта.

Что НЕ теряется: схемы, промпты, проверка цитат и сверка техник
с каталогом ATT&CK перенесены в расширение целиком. Совпадение вердиктов
браузера и сервера проверяется отдельным тестом — один и тот же отчёт
получает одинаковую оценку независимо от того, развёрнут сервер или нет.

### Настройка

Четыре ключа в `policies-local.json`, в блоке
`3rdparty → Extensions → ti-console@soc.internal`:

**Российский провайдер, данные остаются в РФ:**

```json
"llmProvider": "cloudru",
"llmModel": "ai-sage/GigaChat3.5-432B",
"llmApiKey": "<ключ>",
"llmBase": "https://foundation-models.api.cloud.ru"
```

**Claude:**

```json
"llmProvider": "anthropic",
"llmModel": "claude-haiku-4-5",
"llmApiKey": "<ключ>",
"llmBase": ""
```

Перезапустить Firefox. В блоке «Второй этап» появится бейдж
**«внешний API»** фиолетовым и постоянная плашка с именем провайдера.
Если бейдж не появился — ключи не доехали до `browser.storage.managed`;
проверьте `about:policies` → Active, блок `3rdparty`.

⚠️ **Куда расширение может ходить — больше не ограничено манифестом.**
Здесь раньше стояло: «список хостов зафиксирован в `connect-src`, даже если
подменить `llmBase` на чужой адрес, запрос заблокирует CSP». Это перестало
быть правдой, когда появился разбор индикаторов по ссылке: адрес там
произвольный по условию задачи, и директива стала `connect-src 'self' https:`
— то есть разрешён любой https-адрес.

Что удерживает запросы сейчас:

- `<all_urls>` не выдаётся при установке — аналитик подтверждает его сам,
  и видит в `about:addons`;
- разбор по ссылке выключается политикой (`urlFetch: false`) — это
  единственный выключатель, закрывающий исходящий запрос без правки кода;
- `script-src 'self'` не тронут: чужой код на странице расширения
  по-прежнему не выполнится.

Подмена `llmBase` на чужой адрес теперь CSP **не** блокируется. У того, кто
может править `policies.json`, есть админ на машине — то есть угроза, от
которой защищал закрытый список, закрывается не здесь.

### Юридическая оговорка, которую лучше снять заранее

Зарубежный провайдер означает трансграничную передачу. В списках
индикаторов регулярно встречаются адреса электронной почты, а это
персональные данные. Это вопрос к юристам, а не к ИБ, и российский
провайдер снимает его целиком. Я не юрист и решить его за вас не могу.

### Проверка

1. Вставить в умный поиск реальный публичный отчёт (не меньше 200 символов).
2. «Второй этап» → задача «Выжимка с цитатами» → «Проанализировать».
3. Смотреть на счётчик: **подтверждено N, отброшено M**.

Если **всё** ушло в «отброшено» — модель пересказывает вместо цитирования.
Это не повод ослаблять проверку: проверьте, что задана именно та модель,
и что текст не обрезан. Если отброшенных вообще нет ни на одном отчёте —
тоже повод присмотреться: обычно одно-два утверждения из десяти
не подтверждаются, и это здоровая картина.

4. Переключить «Режим данных» на «Клиентские данные» — кнопка анализа
   должна стать неактивной.

## Индикаторы по ссылке и с картинки

Два источника помимо вставленного текста и файла. У каждого своя цена,
и её надо знать до первого использования, а не после.

### По ссылке

Поле «Забрать текст по ссылке» под полем ввода. Понимает дефанг:
`hxxps://evil[.]com/gate.php` вставляется как есть.

**Страница забирается, а не открывается.** Разница принципиальная:
открытая страница выполняется — скрипты, трекеры, фреймы; вредоносная
страница получает исполнение в браузере аналитика, а сайт злоумышленника
— полный отпечаток браузера. Здесь приходит только текст ответа: скрипты
не выполняются, картинки и фреймы не грузятся, куки и реферер
не отправляются.

**Чего это не решает:** запрос всё равно уходит с адреса аналитика.
Инфраструктура, которую вы проверяете, видит обращение и может понять,
что ей интересуются. Для отчёта вендора это безразлично, для панели
управления злоумышленника — нет. Настоящее решение — забор через свой
сервер; пока сервера нет, аналитику об этом сказано строкой под полем,
и убирать её нельзя.

Отключается целиком политикой:

```json
"3rdparty": { "Extensions": { "ti-console@soc.internal": { "urlFetch": false } } }
```

Так и надо сделать, если обращение к инфраструктуре злоумышленника
с адреса компании неприемлемо в принципе. Это решение SOC, а не галочка
аналитика, поэтому оно в политике.

Разрешение на доступ к сайтам Firefox спросит **при первом
использовании**, а не при установке. Расширение, получившее доступ ко всем
сайтам при установке, ничем не отличается от тех, которые мы блокируем
политикой.

Ограничения: 5 МБ, 20 секунд, только `http`/`https`. PDF отдельным
сообщением — скачайте и разберите через «Загрузить файл».

Есть и пункт контекстного меню на ссылке — «TI: забрать ссылку,
не открывая». Он **подставляет** ссылку в поле и останавливается:
решение отправлять запрос принимает аналитик.

### С картинки

Кнопка «Распознать картинку», `Ctrl+V` из буфера, перетаскивание файла.
Появляется только когда модель настроена, и пропадает в режиме
«Клиентские данные».

Распознаёт **модель**, и это надо понимать буквально:

- **автоматической проверки здесь нет и быть не может.** У остальных
  задач есть источник, в котором цитату ищут поиском подстроки. Здесь
  источником были пиксели — сверять не с чем;
- поэтому картинка показывается рядом с распознанным текстом, а текст
  попадает в поле ввода, и **его можно и нужно править**;
- модель обязана перечислить фрагменты, в которых не уверена, — они
  показываются отдельным списком. Это её оценка, а не проверка, но это
  единственное место, где она сообщает, где угадывала;
- индикаторы из распознанного текста достаёт тот же детерминированный
  парсер, что и из любого другого текста. Модель не выдаёт список
  индикаторов — если бы выдавала, проверить его было бы нечем.

**Что ломается чаще всего:** `0` и `O`, `1` и `l` и `I`, `5` и `S`,
`rn` и `m`. В обычном тексте разница незаметна, в домене и хеше решает
всё. Промпт прямо запрещает модели «исправлять» дефанг и достраивать
обрезанные строки, но запрет в промпте — не гарантия. Сверяйте.

Индикаторы, добавленные в кейс с картинки, получают признак
`сверить с картинкой` — он остаётся в кейсе и в экспорте.

**Картинка уходит провайдеру целиком**, вместе со всем, что на ней видно,
включая то, чего вы на ней не заметили: имя хоста в заголовке окна,
учётку в углу, кусок переписки в соседнем окне. Текст перед отправкой
хотя бы читают глазами, скриншот — нет. Поэтому в режиме «Клиентские
данные» распознавание недоступно.

Ограничения: PNG, JPEG, WebP, GIF, до 3,5 МБ. Больше — **вырезайте
фрагмент, а не сжимайте**: уменьшение убивает мелкий шрифт, который тут
и есть предмет распознавания. Вырезанный фрагмент к тому же дешевле
и точнее.

### Если нужно распознавание без отправки наружу

Единственный способ — локальный OCR, и он в проект пока не заложен.
Практический вариант — Tesseract (`tesseract-ocr` с русским языковым
пакетом) на машине аналитика: распознать в файл и загрузить файл. Точность
на скриншотах ниже, чем у модели, зато наружу не уходит ничего.

Встраивание `tesseract.js` прямо в расширение возможно, но это +10…15 МБ
в пакете и правка CSP (`wasm-unsafe-eval`). Делать это стоит тогда, когда
понадобится распознавать клиентские скриншоты, — то есть когда появится
требование, которого сейчас нет.

## FoxyProxy: переключение выхода повкладочно

Второе и последнее стороннее расширение. Ставится `force_installed`
из AMO той же политикой, что и uBlock, — отдельных действий при установке
не требует.

**Зачем.** Фишинговая страница часто показывает разное содержимое
в зависимости от страны посетителя. Проверить это можно только выходя
с разных адресов, причём в соседних вкладках одновременно. Политика
Firefox `Proxy` задаёт один выход на весь браузер и такого не умеет.

**Почему не своя реализация.** Повкладочное переключение требует
разрешений `proxy` и `<all_urls>` — ровно тех, из-за которых мы блокируем
остальные расширения. Своя версия дала бы ту же поверхность атаки без
единого выигрыша.

### Чего нельзя делать с политикой `Proxy`

`Proxy.Locked` обязан оставаться `false`.

FoxyProxy работает через API `proxy.settings`. Политика `Proxy`
с `Locked: true` эту настройку забирает себе, и FoxyProxy перестаёт
переключать выход **молча**: расширение на месте, кнопка нажимается,
трафик идёт как шёл. Диагностируется это плохо, потому что никакой ошибки
не появляется.

Проверка стоит в CI: попытка выставить `Locked: true` при установленном
FoxyProxy роняет сборку с объяснением.

### Что настроить аналитику

Выходы (адреса прокси) FoxyProxy не получает из политики — их заводят
руками в его настройках. Это единственное место во всей установке, где
от аналитика требуется настройка, и обойти это нечем: политика Firefox
чужие расширения не конфигурирует.

Практический вывод: список выходов раздаётся SOC текстом, вместе
с инструкцией. Если выходов больше двух-трёх, имеет смысл подготовить
файл настроек FoxyProxy и раздавать его — расширение умеет
импорт и экспорт.

## Логгер uBlock: разбор поведения страницы без devtools

uBlock Origin стоит ради блокировки. Но в нём есть **логгер запросов**,
и для TI он полезнее блокировки — просто про него не знают, потому что
он спрятан.

Логгер показывает **каждый запрос страницы**: к каким доменам она
обращается, что грузит, что заблокировано. Для подозрительной страницы
это разбор сетевого поведения без Wireshark и без открытия devtools.

### Как открыть

1. Значок uBlock на панели → иконка **списка** (третья в ряду снизу).
   Откроется отдельное окно логгера.
2. Вверху выбрать вкладку, за которой следить, — или **All** для всех.
3. Открыть подозрительную страницу. Запросы появляются по мере загрузки.

Логгер надо открывать **до** загрузки страницы: он не показывает то,
что произошло раньше.

### Что смотреть

| Колонка | Что искать |
|---|---|
| Domain | Домены третьих сторон. Фишинговая страница почти всегда стучится на свою инфраструктуру |
| Type | `xhr`, `script`, `beacon` — активность, а не оформление; `image` на чужом домене часто пиксель-трекер |
| Filter | Что заблокировано. Заблокированный запрос на незнакомый домен — тоже индикатор |
| URL | Параметры запроса: туда утекает то, что ввели в форму |

Правый клик на строке → **Copy** даёт адрес целиком, его можно сразу
вставить в умный поиск консоли.

### Чего логгер не даёт

Тела запросов и ответов. Для этого нужен devtools (`F12` → Network),
и там же видно, что именно ушло в POST. Логгер отвечает на вопрос
«куда обращалась страница», devtools — «что она отправила».

## Если `ERROR_NETWORK_FAILURE`

Это не ошибка политики: схема `file:///` в `install_url` поддерживается
официально, Mozilla пишет прямо — «If installing from the local file
system, use a `file:///` URL». Сообщение означает, что Firefox не смог
получить файл, и причин у этого несколько.

### Сначала — один скрипт вместо перебора

```cmd
powershell -ExecutionPolicy Bypass -File windows\check-install.ps1
```

Проверяет за один прогон: версию и редакцию Firefox (ESR или нет),
наличие и читаемость обоих XPI, метку «скачано из интернета»,
целостность архивов, путь из политики против фактического, настройку
AutoConfig вместе с переводами строк. Ничего не меняет, кроме снятия
метки скачивания, и об этом спрашивает. Вывод достаточно переслать
целиком.

### Две причины, которых не видно ни в Проводнике, ни в about:policies

**1. Проверка подписи не снята.** Самая частая, когда файлы на месте.
Firefox не ставит неподписанные расширения, а `force_installed`
не является исключением. Если AutoConfig (решение 1, вариант A)
не настроен или настроен с ошибкой — расширение не встанет,
и сообщение об этом будет невнятным.

Готовые файлы лежат в `windows/`: `autoconfig.js` и `firefox.cfg`
уже с правильными переводами строк и комментарием в первой строке.
Копировать как есть, не пересохраняя блокнотом:

```
windows\autoconfig.js  ->  <каталог Firefox>\defaults\pref\autoconfig.js
windows\firefox.cfg    ->  <каталог Firefox>\firefox.cfg
```

**2. Метка «скачано из интернета».** Файл, полученный через браузер,
несёт альтернативный поток `Zone.Identifier`. Средства защиты рабочих
станций умеют блокировать чтение таких файлов, и наружу это выходит
ровно такой невнятной ошибкой. Проверка и снятие:

```powershell
Get-Item C:\TI-Console\*.xpi -Stream Zone.Identifier   # есть вывод — метка стоит
Unblock-File C:\TI-Console\*.xpi
```

### Дальше — три проверки по порядку

Каждая занимает секунды и отсекает свой класс причин.

**Шаг 1. Существует ли файл на самом деле.**

```cmd
dir /b "C:\TI-Console\"
```

Именно `dir`, а не взгляд в Проводник: Проводник показывает склейку
настоящего каталога с VirtualStore, и файл может «быть» на экране,
отсутствуя по пути. Ожидается две строки без `(1)` и без второго `.xpi`.

**Шаг 2. Видит ли файл сам Firefox.**

Вставить в адресную строку:

```
file:///C:/TI-Console/ti-console.xpi
```

- Предложил сохранить или открыть файл → путь и права в порядке,
  причина в другом. Переходите к шагу 3.
- «Файл не найден» → файла нет по этому пути. Вернитесь к шагу 1;
  скорее всего сработал VirtualStore при копировании в Program Files.

**Шаг 3. Решающий: временная загрузка.**

Открыть `about:debugging#/runtime/this-firefox` → «Загрузить временное
дополнение» → выбрать `C:\TI-Console\ti-console.xpi`.

Этот способ **полностью обходит проверку подписи**, поэтому он и делит
все причины надвое:

- **Поставилось** → пакет и путь исправны, проблема в подписи или
  в политике. Настраивайте AutoConfig из `windows/`. Заодно у вас уже
  работающее расширение — для показа и первых замеров этого достаточно,
  оно живёт до перезапуска браузера.
- **Не поставилось, ошибка подписи** → нужен AutoConfig либо подпись AMO.
- **Не поставилось, ошибка формата** → пересоберите пакет
  `python3 tools_build_ext.py` и пришлите вывод.

### Запасной механизм, если `file:///` так и не заработает

У Firefox есть вторая политика для установки расширений — `Extensions`,
и она принимает **нативный путь**, а не URL, то есть вопрос кодирования
снимается целиком:

```json
"Extensions": {
  "Install": [
    "C:\\TI-Console\\ti-console.xpi",
    "C:\\TI-Console\\ti-console-theme.xpi"
  ],
  "Locked": ["ti-console@soc.internal", "ti-console-theme@soc.internal"]
}
```

Отличие от `ExtensionSettings`: `Install` ставит расширение один раз
при первом запуске, а не удерживает его установленным. `Locked`
запрещает пользователю его выключить. Белый список из `ExtensionSettings`
при этом продолжает работать и блокировать всё постороннее.

Добавляется в `policies-local.json` рядом с `ExtensionSettings`.
Держать оба механизма одновременно не нужно — это вариант на случай,
если первый не заработает.

## Что изменится, когда появится сервер

Переход не требует переустановки — только замены файла политики.

| Шаг | Что делается |
|---|---|
| 1 | Развернуть сервер по RUNBOOK, этапы 1–6 |
| 2 | Взять `policies/policies.json` (основной, не локальный), подставить адрес сервера и токен |
| 3 | Раскатать новый файл политики тем же средством |
| 4 | Перезапустить Firefox |

После этого появляются: автоматическое обогащение, метапоиск через
SearXNG, единый реестр инструментов с обновлением без перевыпуска
расширения, журнал аудита. Позже — краулер и анализ моделью.

Ничего из того, что работало локально, при этом не меняется:
разбор индикаторов, кейс и отчёт как выполнялись на машине,
так и продолжают.

## Первый запуск падает, второй проходит

Симптом: браузер при первом запуске закрывается сам, повторный запуск
проходит нормально.

**Причина не установлена.** Ни одна известная мне часть расширения
не может уронить процесс Firefox: расширение — это JavaScript
в песочнице, его ошибки роняют максимум фоновую страницу. Поэтому
ниже не «решение», а порядок проверок, который отсекает варианты.
Выполняется за пять минут.

### Шаг 0. Собрать данные одним скриптом

```
powershell -ExecutionPolicy Bypass -File collect-startup-issue.ps1
```

Скрипт **при закрытом браузере** собирает всё, что нужно шагам 1–3,
в один файл `ti-startup-issue.txt` на рабочем столе: висящие процессы,
блокировку профиля, файлы отчётов о падениях на диске и записи о
firefox в журнале событий Windows за неделю.

Он только читает — ни одной записи, ни одного сетевого вызова.
Адресов посещённых страниц и содержимого кейсов в отчёте нет.

Шаги ниже описывают то же самое руками, если запускать скрипт
не хочется.

### Шаг 1. Было ли падение вообще

```
about:crashes
```

Важная оговорка: **пустой `about:crashes` не доказывает, что падения
не было.** Если процесс упал на очень раннем старте, сборщик отчётов
Firefox просто не успел инициализироваться, и следа там не останется.
Запись при этом остаётся в журнале событий Windows — его смотрит
шаг 0 или шаг 3.

Это первое и главное, потому что ответ делит задачу пополам.

- **Есть отчёты с сегодняшней датой** — процесс действительно упал.
  Откройте верхний отчёт, найдите строку `Signature`. Она и говорит,
  что упало: графика (`gfx`, `d3d`, `dxgi`), сеть, JS-движок.
  Пришлите сигнатуру.
- **Отчётов нет** — падения НЕ БЫЛО. Браузер закрылся штатно, и это
  другая задача: шаг 2.

### Шаг 2. Если отчётов нет — остался прошлый процесс

Самый частый случай на Windows, и к расширению он отношения не имеет.
Предыдущий `firefox.exe` не завершился, профиль заблокирован, первый
запуск упирается в блокировку и закрывается; ко второму запуску
процесс успевает умереть.

```
tasklist | findstr firefox
```

Если в списке есть `firefox.exe` при закрытом браузере — это он.
Проверка: завершить процесс и запустить браузер. Если запустился
с первого раза — причина найдена, и она в том, что Firefox долго
выгружается (обычно из-за сеанса с большим числом вкладок).

### Шаг 3. Проверить, при чём здесь расширение

```
Меню → Справка → Режим устранения неполадок
```

Запуститься так дважды подряд (в этом режиме расширения отключены).

- **Падает и там** — расширение ни при чём. Смотрите видеодрайвер
  и антивирус.
- **Не падает** — виновато одно из четырёх расширений. Отключайте
  по одному: uBlock Origin, FoxyProxy, тема, TI Console. Порядок
  именно такой: первые два — чужой код, наш — последний.

### Шаг 4. Гипотеза про домашнюю страницу

Проверять, только если шаги 1–3 ничего не дали.

С 0.22.0 домашняя страница — это страница расширения
(`chrome_settings_overrides.homepage`). При старте браузер открывает
её раньше, чем расширение полностью загружено, — теоретически здесь
возможна гонка.

Проверка: `about:preferences#home` → «Домашняя страница и новые окна» →
временно поставить «Пустая страница», перезапустить браузер дважды.

- **Перестало падать** — гипотеза подтвердилась, сообщите: домашнюю
  страницу переведём на отложенное открытие.
- **Падает по-прежнему** — домашняя страница ни при чём, верните
  «Расширение (TI Console)».

### Чего делать НЕ надо

Переустанавливать расширение «на всякий случай»: это меняет UUID
и стирает наблюдение, не проверив ни одной гипотезы.

## Если что-то не работает

| Симптом | Причина | Что делать |
|---|---|---|
| `Unknown policy: _1_обновления` и подобные в Errors | Развёрнут исходник `policies.json` вместо сгенерированного | Взять `policies-local.json`; в нём комментариев нет |
| `private_browsing … Expected "boolean"` | Старая версия политики | Исправлено в 0.12.3: значение `true`, а не `"force_enabled"` |
| `Download failed - ERROR_NETWORK_FAILURE - file:///…` | Файла нет по этому пути, либо он недоступен на чтение. Политика тут ни при чём: синтаксис `file:///` для `install_url` поддерживается официально | Лестница проверок ниже |
| Тема не встала, расширение встало | Повреждён пакет темы | Пересобрать `python3 tools_build_ext.py`; сборщик проверяет манифест темы и падает, если внутри объекта `theme` оказался лишний ключ |
| Расширение не ставится, ошибка подписи | AutoConfig не применился | Проверить: первая строка обоих файлов — комментарий, переводы строк LF |
| Пункты «TI: …» пропали из правого клика после перезапуска | Сборка до 0.25.0: меню создавалось только при установке расширения | Обновить XPI до 0.25.0 и выше |
| Новая вкладка — страница Mozilla | Другое расширение перехватило `newtab` | `about:addons`; белый список должен был это предотвратить — проверить, применилась ли политика |
| Новая вкладка — консоль, а домашняя страница — Firefox с полем поиска | Установлена сборка расширения до 0.22.0: до неё домашнюю страницу пытались задать политикой, а так её задать нельзя | Обновить XPI. Политику при этом тоже обновить: `Homepage` из неё удалена, и старая политика перебьёт настройку расширения |
| На домашней странице плитки сайтов и спонсорские плитки | Нет политики `FirefoxHome` (добавлена в 0.22.0) | Взять политику 0.22.0 и выше; проверить `about:policies` → Active → `FirefoxHome` |
| Домашняя страница пустая, лисы нет | Смотрите не на консоль, а на страницу Firefox; либо консоль открыта, но уже что-то разобрано — лиса уходит при первом результате | Пункты приёмки 38–40 |
| Политика не применяется на Windows | Файл не там | Именно `distribution\policies.json` в каталоге установки Firefox, а не в профиле |
